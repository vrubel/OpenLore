# Change: консолидация решений и сервер MCP не оставляют процессов

Локальное изменение форка `vrubel/openlore` для карточки PDLC-3414 (PDLC-3407 п. 3) эпика Jira PDLC-3402 «Утечки
процессов Maestro», канон линии — PDLC-3411. Эпик хранилища OpenSpec продукта — `pdlc-3402-process-leaks` в
`vrubel/pdlc-maestro-spec-store` (коллектор `collector/pdlc-3402-leaks`): требование F-OPS-021.R3, задача 3.1 его
`tasks.md`. База — коммит тега пина установщика `v2.1.3-ru20` (`24055a01e7fd3385739a37efa0b81b3c2f724cd8`;
`scripts/forks.lst:108` pdlc-core `9f42086a`), коллектор `collector/pdlc-3402-leaks`. Источник требований — пакет
источников `pdlc-3402-leaks-v1` (`vrubel/pdlc-source-packs`, коммит `acdbb9338105a25a4ae0cdf898b07300990c663d`).

## Why

Инструмент `record_decision` после записи решения вызывает `spawnConsolidateBackground`
(`src/core/services/mcp-handlers/decisions.ts:28-53`, вызов — строка 174), который порождает
`openlore decisions --consolidate` с `detached: true` и `unref()`. Процесс консолидации живёт в своей группе и
переживает сервер `openlore mcp`, которого Maestro гасит: на каждый вызов остаётся `node` и, возможно, CLI агента, до
~5 минут (`leak-report.md` пакета, строка 19). Сервер `openlore mcp --http` не следит за своим stdin, поэтому после
аварийной гибели родителя — сервера Maestro — живёт до перезагрузки и копится с каждым падением (там же, строка 1 и
исправление И1).

## What Changes

- **mcp-handlers** (ADDED `DecisionConsolidationDoesNotOutliveMcpServer`): консолидация решений гасится при закрытии
  сервера (`close`, в том числе по SIGTERM) и порождается без отделения, в группе сервера MCP, — оба способа
  PDLC-3407 п. 3: одного первого не хватает для SIGTERM номеру сервера, по которому сервер выходит, детей не гася. После
  закрытия сервера теми способами ядра Maestro, которые покрывают оба способа (SIGTERM номеру сервера, по которому он
  выходит; сигнал группе, в которой стоит сервер; гашение дерева по номерам), консолидации и её потомков нет.
- **cli** (ADDED `McpServerExitsOnStdinCloseWhenAsked`): сервер `openlore mcp`, запущенный с ключом
  `--exit-on-stdin-close`, выходит по закрытию stdin — в режиме stdio и с `--http`. Без ключа поведение прежнее: stdin
  из `/dev/null` (systemd, `nohup`, docker без `-i`) сервер не останавливает.

Новых отказов, остановок, обязательных шагов и условий запуска изменение не вводит: выход по закрытию stdin — только
по явному ключу, а ядро передаёт ключ только бинарю, который его знает.

## Пределы механизма

SIGKILL одному номеру процесса сервера (`killAllOpenloreHttpSync` и `close()` по сроку,
`scripts/lib/ports/openlore-http.mjs:237`, `:443` pdlc-core `9f42086a`) не перехватывается, и неотделённая
консолидация в группе сервера его переживает: ни один из двух способов PDLC-3407 п. 3 этого случая не покрывает. Это
предел механизма, а не обещание. На Windows этот случай закрывает требование эпика F-OPS-023.R3 (PDLC-3409 п. 3):
`close()` и `killAllOpenloreHttpSync` гасят дерево через `killSubtree`. На Linux и macOS его не закрывает ни одно
требование: консолидация выходит сама, до ~5 мин (`leak-report.md` пакета, строка 19).

## Связь

- Тег форка и пин установщика (`scripts/forks.lst` pdlc-core) — только по отдельному слову владельца, записанному в
  PDLC-3414 (план линии, комментарий 32184): без него тег не ставится и пин не двигается.
- Ядро сейчас запускает `openlore mcp --http` со stdin `ignore` (`scripts/lib/ports/openlore-http.mjs:422-428`
  pdlc-core `9f42086a`). Ядро передаёт ключ `--exit-on-stdin-close` и трубу stdin только тогда, когда установленный
  бинарь ключ знает (асинхронная проба справки `openlore mcp --help`, измеренный итог по идентичности бинаря, отказ
  порождения не запоминается), иначе запускает как прежде с
  предупреждением; к пину это не привязано (задачи 11.1–11.2 локального изменения ядра). Порядок не жёсткий в обе
  стороны: новый форк без ключа ведёт себя как прежний, старый форк получает запуск без ключа.
- Что не воспроизводится на Linux-раннере (macOS, Windows), отмечается явно; живое подтверждение снимает владелец.
